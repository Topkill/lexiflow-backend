## 当前仍未解决的场景

以下只列“部分修复”剩余的部分和“未修复”问题。已经完全修复的 P1-1、P2-1、P2-2、P3-1 不再重复。

### P1-2：完形降级后计划掌握数没有同步（已修复）

原场景：计划中单词 A 已是 `MASTERED`，计划的 `masteredCount=1`。用户在完形填空中把 A 答错，统一调度器会把 A 的 `repetition` 清零，并把状态改为 `LEARNING` 或 `DIFFICULT`，但完形服务没有同步减少计划的 `masteredCount`。之后 A 经过正式复习重新达到 `MASTERED` 时，卡片路径可能再把计划计数加一，使计划显示虚高。

2026-09-20 起计划响应中的已掌握数不再读取计划冗余字段，统一按 `user_word_state` 实时聚合（`StudyPlanService.countMasteredWords` 按 用户＋词库＋`MASTERED` 计数），`DailyTaskService.updateStudyPlanProgress` 不再维护冗余计数。无漂移数据源，无需重算存量计划计数；原 `mastered_count` 列保留但代码不再读写。

### P1-3：反馈并发已有串行化，但数据库缺少最终唯一约束（基本修复后的剩余项）

场景：用户在两个设备上几乎同时提交同一篇完形。当前代码先锁定该用户行，第二个请求会等待第一个事务完成，然后读取已存在的作答并返回，因此正常服务入口不会重复处理。

剩余风险：`cloze_attempt` 表本身没有“用户＋题目”的唯一约束。如果以后新增入口、批处理或维护脚本没有取得同一把用户锁，数据库仍允许插入两条作答。当前结论也只经过静态检查和构建，没有在真实 MySQL 上验证锁等待、事务隔离和异常回滚。

剩余工作：为完形作答增加数据库唯一约束，并验证并发提交。用户行锁目前覆盖正确性，唯一约束用于让数据库自身也能守住该业务不变量。

### P1-4：同词重复展示已移除（已修复）

原场景：单词 A 今天既到期，又存在于未解决错词中。任务生成时可能同时创建 A 的一个 `REVIEW` 项和一个 `EXTRA` 项，用户完成 REVIEW 后仍会在 EXTRA 组再次遇到 A。

2026-09-20 起普通每日任务不再生成 `EXTRA` 任务项（`generateTodayTask` 只插入 `NEW`/`REVIEW`），该场景不再可达。错词召回由间隔算法在 UNKNOWN 反馈后重排至次日承担；需要主动加练时使用独立错词专项复习入口（`WRONG_WORD_PRACTICE`），其任务项仍为 `EXTRA`，且不影响当日每日任务。

### P2-3：完形失败仍是长期调度信号，提示使用无法识别（部分修复后的剩余项）

场景一：用户知道单词含义，但在完形中因为拼写、词形变化或题目语境问题答错。如果这是当天该词第一次 UNKNOWN，系统仍会扣 EF、清零 repetition，并安排次日复习。

场景二：用户打开了词性或中文释义提示后答对。请求没有携带提示等级，事件与完全独立答对相同；这次正确只记统计，不恢复 EF。反过来，用户看过提示后仍答错，也可能触发当天一次正式惩罚。

已修复的部分是同日卡片、EXTRA、专项和多篇完形共享一次 UNKNOWN 惩罚额度，不会因多入口反复扣 EF。剩余工作是决定完形错误是否应直接改变长期调度，并上传提示等级、区分拼写／词形错误与真正不认识。

### P2-4：MASTERED 和 DIFFICULT 仍是粗粒度标签（未修复）

场景一：新词首次答对后 repetition=1，次日正式答对变为2，再按 3 天间隔答对一次就变成 `MASTERED`。它只证明了几次较短周期的正式成功，没有最低保持天数或较长间隔要求。

场景二：用户几个月内零散答错同一个词三次，累计 `wrongCount>=3` 后会被标为 `DIFFICULT`，系统无法区分“最近连续困难”和“长期偶发失误”。下一次正式答对又会把标签改回 `REVIEWING`。

结果：MASTERED 可能过早，DIFFICULT 又可能受很久以前的失败影响。错词表、困难标签和掌握标签仍是不同口径，一个词可能在不同页面呈现看似矛盾的状态。

剩余工作：MASTERED 加入跨日次数、最低保持时长或最低间隔；DIFFICULT 改用近期失败窗口或连续失败规则，并明确普通答对何时解决错词。

### P2-5：旧任务和完形流程仍会推迟新到期词（未修复）

场景一：用户昨天开始了一组任务但没有完成，今天又有一批单词到期。系统优先返回昨天已开始的任务，而且不会把今天新到期的词补进已经被触碰的旧任务。用户必须先完成旧组，新的到期词才能进入后续任务。

场景二：用户已经完成一组卡片，但对应完形还没提交，或者 AI 完形生成暂时失败。入口会优先返回这个等待完形的任务，新一组到期复习可能继续等待。

场景三：同一组中前端按 `NEW → REVIEW → EXTRA` 展示。即使复习词已经逾期，用户也会先完成新词组。

剩余工作：提供独立的到期复习入口；允许完形稍后完成而不阻挡下一组；积压时优先 REVIEW，并动态减少或暂停 NEW。

### P2-6：固定上海自然日，没有使用用户时区或实际间隔（部分修复后的剩余项）

场景一：用户人在洛杉矶，本地日期边界与上海相差数小时。系统仍按上海零点重置“每日一次惩罚”和正式复习资格，用户本地同一天内的两次学习可能被划入两个业务日，或本地跨日后仍落在同一个业务日。

场景二：用户在上海时间 23:59 学习失败，`nextReviewDate` 设置为次日。零点后日期已经满足到期条件，因此所谓“1 天后”可能只经过几分钟，而不是至少 24 小时。

场景三：用户逾期 1 天和逾期 30 天后答对，当前算法都从原 interval 和 EF 计算下一间隔，不使用真实经过天数。

已修复的部分是服务端不再受 JVM 或数据库默认时区漂移影响，统一使用 `Asia/Shanghai`。剩余工作是确定产品究竟采用统一业务时区还是用户时区，并决定是否记录、使用实际间隔和逾期程度。

### P2-7：缺少运行验证和完整算法快照（未修复）

场景一：如果部署时漏执行迁移，首次反馈会访问不存在的 `study_daily_word_effect` 或新增事件字段，构建仍然成功，但运行时会直接报数据库错误。

场景二：两个设备同时反馈、事务中途异常或 MySQL 隔离级别与预期不同，只有真实数据库并发验证才能确认锁等待、回滚和计数结果；当前没有这类验证。

场景三：以后发现某个词间隔异常，事件只能说明 attemptType、businessDate 和本次算法是否生效，没有保存变更前后的 EF、repetition、interval，也没有算法版本，无法只靠事件完整回放当时的计算。

场景四：前端刷新、响应丢失和局域网 HTTP 下的请求重试虽已实现，但未完成真实浏览器与后端联调。

剩余工作：部署前验证迁移；补并发、跨日和接口联调；后续如需要评估算法效果，再增加算法版本及调度前后快照。按照当前要求，本次没有为这些场景新增测试代码。

## 1. 2026-09-08 结论（历史）

**当前算法可以支撑 MVP 的基础复习闭环，但还不够完善，不宜直接将其输出解释为可靠的长期记忆水平。**

“认识／不认识”两档本身可以保留。主要问题在于反馈采集、日内重练和跨日调度混在一起，以及两档映射与 EF 更新公式不完全匹配：

1. **复习词先看释义再回忆的问题已在 2026-09-19 本地修复**；首次反馈前不再展示中文释义，后续重练与跨日计数边界仍见 P2-2。
2. **EF 只降不升**；累计四次实际进入调度器的“不认识”就降到下限，后续再多次“认识”也无法恢复。
3. **普通完形填空只在答错时影响调度**，重新生成练习也能继续降级同一单词；这属于已明确保留的产品取舍，但有累积惩罚风险。
4. **同一任务重练成功被计入连续成功次数**，跨日补做又可能一直复用之前的失败去重结果。
5. 新增的**普通任务错词加练可能对同一词重复调度**；原有已掌握统计不同步、跨入口词状态并发缺少保护、旧任务阻挡新到期复习等问题仍需处理。（2026-09-20 已移除普通任务自动错词加练，该重复调度入口不再存在；“普通每日任务中的 EXTRA 会参与 SM-2”的评估仅对 2026-09-20 之前的实现成立，此后 EXTRA 仅存在于错词专项任务。）

新分支已改善同一任务项提交幂等与任务完成数递增，不能再把这一部分描述成完全没有保护；它也没有解决同词跨任务项／跨入口的调度边界。

建议先修正反馈与调度边界、数据一致性，再调整参数；当前没有必要仅为改善这些问题就改成更多按钮或彻底更换算法。

本文只更新说明文档，未修改业务代码。结论来自新旧源码差异、静态调用链检查、测试源码审阅和数值复算；未运行应用、连接数据库、进行并发压测或长期记忆效果实验。下文区分确定行为、设计局限和待运行验证的风险。

## 3. 单词状态与作用范围

调度状态按 **用户 + 词库 + 单词** 隔离，数据库唯一约束还包含逻辑删除标记。`planId` 只是最近关联计划，不是调度状态的主维度。

因此，同一个用户在不同词库中的同一单词不会自动共享这份记忆状态；同一词库下切换计划也不会天然产生一份独立状态。调用时传入非空 `planId` 才覆盖原值，普通完形填空传入 `null`，已有状态的计划归属保持原值。

| 字段 | 初始值 | 实际含义 |
| --- | --- | --- |
| `masteryStatus` | `NEW` | 当前掌握标签 |
| `learned` | `false` | 是否收到过进入调度器的反馈；第一次答错也会变成 `true` |
| `repetition` | `0` | 自最近一次失败之后进入调度器的连续成功次数；包含新词确认、普通重练成功及普通每日任务的 `EXTRA` 成功 |
| `intervalDays` | `0` | 当前安排的复习间隔，单位为日 |
| `easinessFactor` | `2.50` | 间隔增长因子 EF；越大，后续间隔增长越快 |
| `nextReviewDate` | 未设置 | 下一次到期的日历日期 |
| `wrongCount` / `correctCount` | `0` / `0` | 调度器接收的累计失败／成功次数，不等同所有练习作答次数 |
| `lastStudiedAt` | 未设置 | 最近进入调度器的反馈时间 |
| `lastReviewedAt` | 未设置 | 仅 `scene=REVIEW` 时更新；完形填空失败不更新此字段 |

`wrong_word` 错词表与 `user_word_state` 是两套状态。独立专项练习能更新错词记录而不更新调度状态，所以错词已解决不等于 EF 已恢复，也不等于已掌握。2026-09-20 起普通每日任务不再生成 `EXTRA` 项，错词加练仅经独立专项入口，不再同时影响两套状态。

## 4. 核心计算规则

### 4.1 两档反馈如何映射

| 用户反馈 | 枚举 | 质量分 q | EF 增量 |
| --- | --- | --- | --- |
| 不认识 | `UNKNOWN` | 2 | −0.32 |
| 认识 | `KNOWN` | 4 | 0.00 |

代码采用：

```text
EF_next = max(1.30,
  round2(EF + 0.10 - (5-q)×0.08 - (5-q)²×0.02))
```

其中 `round2` 使用 `HALF_UP` 保留两位小数。代码先计算本次新 EF，再更新间隔；成功时 EF 不变，所以在当前两档输入下，新旧 EF 的计算顺序不影响成功间隔。

EF 的下降轨迹是：

```text
2.50 → 2.18 → 1.86 → 1.54 → 1.30
```

这里四次失败可以跨多天、多个任务，中间可以夹杂任意次成功；必须是实际进入核心调度器的四次失败，同一任务内被过滤掉的重复失败不算。

### 4.2 认识时

```text
repetition_next = repetition + 1

若 repetition_next = 1：interval_next = 1
若 repetition_next = 2：interval_next = 3
若 repetition_next ≥ 3：
  interval_next = max(1, HALF_UP(max(interval_old, 3) × EF_next))

correctCount += 1
masteryStatus = repetition_next ≥ 3 ? MASTERED : REVIEWING
```

`HALF_UP` 在这里表示四舍五入到整数天。

### 4.3 不认识时

```text
repetition_next = 0
interval_next = 1
wrongCount += 1
masteryStatus = wrongCount ≥ 3 ? DIFFICULT : LEARNING
```

无论原来安排 3 天、50 天还是更长，失败都回到 1 天；保留累计错误数并降低 EF。

### 4.4 共同更新

```text
learned = true
nextReviewDate = 服务器默认时区的今天 + interval_next
lastFeedback = 本次反馈
lastStudiedAt = 当前时间
若 scene = REVIEW：lastReviewedAt = 当前时间
```

算法没有读取实际距离上次反馈的时长，也没有使用逾期天数、答题耗时或目标记忆保持率来计算下一间隔。`scene` 主要区分时间戳，不改变核心间隔公式。

### 4.5 数值示例

在对应 EF 固定、每次成功都被接收的条件下，各次成功后的间隔如下；这是间隔长度，不是从首次学习开始累计的天数。

| 连续成功次数 | EF=2.50，未发生失败 | EF=1.30，已降到下限后重新连续成功 |
| --- | --- | --- |
| 1 | 1 天 | 1 天 |
| 2 | 3 天 | 3 天 |
| 3 | 8 天，标记已掌握 | 4 天，标记已掌握 |
| 4 | 20 天 | 5 天 |
| 5 | 50 天 | 7 天 |
| 6 | 125 天 | 9 天 |
| 7 | 313 天 | 12 天 |
| 8 | 783 天 | 16 天 |

例如 9 月 8 日首次认识，按期分别在 9 月 9 日和 9 月 12 日再次认识，会在 9 月 12 日被标为 `MASTERED`，下次安排 9 月 20 日。这个标签不等于已经验证了数周或数月的保持能力。

## 5. 哪些行为会影响调度

### 5.1 卡片的实际流程

前端默认按 `NEW → REVIEW` 分组，每组再分段；`EXTRA` 分组仅出现在错词专项任务中。2026-09-19 修复后，复习组首轮各段直接进入 `confirm`；新词和重练仍先进入 `learn`，然后进入 `confirm`。

```text
学习阶段：展示释义、例句译文 → 下一张（不提交调度反馈）
回忆阶段：
  点击不认识 → 提交 UNKNOWN → 加入重练集合
    复习首轮：显示当前词释义 → 继续复习 → 下一词判断／本轮结束后重练
  点击认识 → 显示中文释义选择题
    选对 → 提交 KNOWN → 该任务项 DONE
    选错 → 提交 UNKNOWN → 加入重练集合
重练：再次学习、回忆，直到该任务项成功
```

所以“点击认识”本身不会立即记为成功，还需要选对选项。当前选项正确性由前端判断，反馈接口接收 `feedback`，不接收选项用于后端复核；选择题不可用时前端提示重试，不能直接完成认识反馈。所有正常卡片反馈目前传 `durationSeconds: 0`。

### 5.2 入口对照

| 行为 | 更新调度？ | 实际结果 |
| --- | --- | --- |
| 普通新词／复习词首次失败 | 是 | q=2、EF 降低、连续成功归零、明日到期，任务项仍待完成 |
| 同一普通任务项再次失败 | 否 | 前端失败集合过滤；后端 CAS 要求待完成且原反馈不是 `UNKNOWN`，重复失败返回当前结果，不新增学习事件 |
| 普通任务首次成功 | 是 | q=4，推进连续成功和间隔，任务项完成 |
| 普通重练最终成功 | 是 | 即使刚刚失败过，也按一次成功推进连续次数；失败后的首次成功仍安排 1 天 |
| 已完成任务项顺序重提同一 `KNOWN` | 否 | CAS 不再领取，确认状态已为 `DONE/KNOWN` 后返回当前结果；不是持久化的首次响应快照 |
| 已完成任务项改提 `UNKNOWN` 等不匹配反馈 | 否 | 返回不可提交错误 |
| 普通每日任务自动加入的错词 `EXTRA` | — | 2026-09-20 起已移除；普通每日任务只含 `NEW`/`REVIEW`，错词仅通过独立专项入口加练 |
| 独立 `WRONG_WORD_PRACTICE` 卡片任务 | 否 | 记录事件、处理错词状态与任务进度；重复反馈受 CAS 领取规则限制 |
| 普通完形填空答错／漏答某空 | 是 | 该空对应词按 `UNKNOWN`、`QUIZ` 更新；答错也进入错词表 |
| 普通完形填空答对 | 否 | 记录作答和事件，不推进调度、不恢复 EF |
| 重新生成普通完形填空后答错 | 是 | 新题仍能对同一词再次降级，没有跨题／按日去重 |
| 错词专项任务关联的完形填空 | 否 | 答错仍更新错词记录，但跳过调度 |

同一篇完形填空有“已提交”查询检查；重新生成产生的新题不受上一题提交记录限制。是否属于错词专项由关联的 `DailyTask.taskType` 判断。

前端新增逐步显示词性、中文释义的提示，但提交仍只有答案与耗时，不包含提示等级；后端调度也没有提示等级分支。普通每日任务即使包含 `EXTRA`，其关联完形填空仍属于普通任务来源，答错不会因此跳过调度。

### 5.3 同日失败后成功的真实结果

假设某词原来 EF=2.50、连续成功 5 次、间隔 50 天：

| 步骤 | 连续次数 | 间隔 | EF |
| --- | --- | --- | --- |
| 本次首次失败 | 0 | 1 天 | 2.18 |
| 同一任务重练再次失败 | 0 | 1 天 | 2.18 |
| 本轮最终成功 | 1 | 1 天 | 2.18 |
| 次日复习成功 | 2 | 3 天 | 2.18 |

对**同一个任务项**，不能把当前行为描述成“当天失败后成功就跳到 3 天”；同日补对只把连续次数推进到 1。但它确实让当天重练成功与一次独立的间隔复习成功共用同一计数。新分支还可能为同一词创建另一个 `EXTRA` 项，其成功可以在当天继续推进到 2，详见 P1-4。

## 6. 到期词如何进入任务

每日任务按当前主计划的词库选择：`learned=true`、下次日期非空且 `nextReviewDate ≤ today` 的单词，不排除 `MASTERED`。

排序依次为：到期日期升序 → 累计错误次数降序 → 更新时间升序 → ID 升序。每组最多取 `reviewWordsPerGroup`；未配置时回退为每组新词数的两倍，每组新词数未配置时默认 20。**这是每组配额，不是一天只能复习这么多。**

新生成普通任务时，还会从当前词库选取最多 `newWordsPerGroup` 个未解决错词作为 `EXTRA`。排序为错误次数降序 → 最近错误时间降序 → ID 升序；这个查询**不判断到期日期，也不排除本组新词或复习词**。三类候选都为空才认为无任务，因此只有未解决错词时也可以生成普通任务。任务项唯一约束包含 `item_type`，允许同一词分别以 `REVIEW` 和 `EXTRA` 入组。

补入已有任务时，会排除该任务中已存在的词，并扣除已占用的复习槽位。独立“复习”页主要展示到期列表，默认可跨词库查看，列表次级排序与任务选择不同；实际进入学习组仍跟随主计划词库。

任务入口还会：

1. 优先返回当天已完成卡片、但尚未提交关联完形填空的普通任务。
2. 否则继续已有待完成普通任务；旧任务完全未开始时可以滚动日期并补到期词。
3. 旧任务只要已有完成项或反馈，就不自动同步今天新到期的词。
4. 没有上述任务时生成下一组，同时取新词、复习词和未解决错词加练。

普通任务本次完成时，后端在事务提交后预热完形填空，前端也支持按异步任务 ID 进入生成等待页。生成任务复用、Redis 生成锁和 RabbitMQ 异步执行改善的是生成链路，未改变“当日完成组需提交完形填空后再进入下一组”的选择规则。

后端为复习词设置靠前的序号，但前端会重新按 `NEW → REVIEW → EXTRA` 分组，所以当前交互并不是复习优先。

## 7. 与原版 SM-2 的关系

本项目保留了 EF 初值 2.50、下限 1.30、质量分更新公式和按间隔乘 EF 的基本结构；主要变化是只保留 q=2/4、第二次成功间隔改为 3 天，并使用四舍五入。原文使用 0–5 评分、起始间隔 1/6 天和向上取整。原文还包含会话结束后的当日补练安排，不能据此把所有补练都等同独立跨日成功。[SM-2 原始算法说明](https://www.super-memory.com/english/ol/sm2.htm)

**缩短第二次间隔和保留两档是可以讨论、验证的设计选择，不应仅因偏离原版就判定为 bug。** 下节重点评估当前流程是否能形成一致、可靠的调度输入与结果。

## 8. 缺陷与局限评估

优先级：P1 表示优先处理的核心反馈或数据正确性问题；P2 表示影响长期使用的策略／流程问题；P3 表示低频防御性改进。这里不是线上故障严重等级。

### P1-1：复习前先展示答案，削弱了反馈有效性（已修复）

2026-09-19：已修复普通复习词首轮先展示答案的流程。新建流程、换组、换段及缓存恢复均直接进入认识／不认识；不认识后才显示当前词释义。前端生产构建通过；流程测试是此前修复阶段的记录，本轮算法升级按要求未运行测试，未宣称完成端到端验证。

以下为修复前的问题依据，保留用于追溯：

**确定行为，效果幅度尚未量化。** S7 的初始化、换段和换组均进入 `PHASE_LEARN`，S8 显示释义和例句译文，复习词没有跳过这一步。

触发：昨天学习的词今天到期，用户先浏览该段全部释义，再在回忆阶段选对。后端会把这次成功用于扩大下次间隔。

影响：无法区分“隔了一天仍记得”和“本来忘了，刚刚看过又记住”。即使间隔公式完全正确，输入也可能高估保持能力。选择题本身提供选项提示，衡量的也主要是释义辨认能力。

建议：到期复习词直接进入首次回忆；首次结果作为长期调度依据。失败后再展示答案并进入重学。新词可以继续先学习后确认。

### P1-2：完形填空降级未同步计划已掌握计数（未修复）

2026-09-19：问题仍存在。完形反馈已进入统一调度事务，但 `ClozeQuizService` 仍未根据调度结果的旧／新掌握状态维护计划 `masteredCount`。

2026-09-20：已解决。计划不再读取冗余 `masteredCount`，改为按 `user_word_state` 实时聚合，漂移源已移除。

**确定的代码路径遗漏。** S5 调用调度器后没有使用其返回的旧／新掌握状态，也没有执行 S9 的计划计数更新。

最小过程：

1. 某词为 `MASTERED`，所属计划 `masteredCount=1`。
2. 普通完形填空该词答错，状态变为 `LEARNING` 或 `DIFFICULT`。
3. 计划仍为 1；总览缓存未命中／过期重新按词状态聚合后变为 0。新分支总览有 30 秒缓存，显示不一定立刻变化。
4. 该词后续重新成为 `MASTERED`，卡片路径又给计划加 1，可能变为 2。

建议：统一掌握状态变更与计数维护入口，或按一致范围实时聚合；对已有冗余计数提供重算。普通完形填空传 `planId=null`，更新时还需明确由词状态归属还是其他计划范围承接，不能随意使用当前主计划。

### P1-3：同任务项保护已有改进，同词跨入口并发仍有缺口（基本修复）

2026-09-19：卡片与完形提交现在都会在读取业务状态前锁定当前用户行，并在同一短事务内更新每日额度、词状态、事件、错词和任务。同用户的不同任务项、设备及入口会串行处理，首次词状态创建也受保护。完形作答表仍没有用户＋题目的数据库唯一约束，安全性依赖服务层事务锁；真实数据库并发尚未压测。下列“仍存在的边界”描述的是修复前基线。

**新分支已部分修复，不能沿用旧版“没有保护”的结论。** S14 使用带条件的 SQL 更新领取提交：必须仍为 `PENDING`，失败提交还要求原反馈不是 `UNKNOWN`。只有更新成功才执行后续调度和事件写入；同样结果重提走当前状态返回。任务 `done_count` 使用 SQL 原子递增。这些操作在卡片反馈事务内，构成同任务项的一次处理保障。

仍存在的边界：

- 不同任务项（如同词的 `REVIEW` 与 `EXTRA`）有不同 CAS 目标，仍可同时修改同一份 `UserWordState`；卡片和完形填空也不共用词状态锁。状态依旧按“查询 → Java 中计算 → updateById”写回，可能丢失更新。
- 普通完形填空**作答提交**仍是先查“已提交”再插入，`cloze_attempt` 没有用户与题目的唯一作答约束。生成阶段的 Redis 锁不能保护这一提交入口。
- 调度实体没有 `@Version`。计划实体虽有版本字段，卡片路径未检查 `studyPlanMapper.updateById(plan)` 的更新条数；不同任务项并发修改计划时，需验证并处理版本冲突，避免词状态和计划计数不一致。
- 同任务项的条件更新能避免重复应用，但竞争失败后的普通查询能否立即读到另一事务的新状态，仍需在实际隔离级别下验证；已有 mock 测试不能证明该数据库行为。

建议：保留已有 CAS 和原子计数，补同词跨入口的串行化／版本重试、题目作答唯一约束以及计划更新冲突处理。并发结果尚未压测，不能把以上风险写成已观测的线上事故。

### P1-4：新增普通错词加练可重复或提前推进同一词的调度（部分修复）

2026-09-19：算法重复推进已修复。EXTRA 成功按 `IN_DAY_RETRY` 记录，不增加 EF、正式 repetition 或间隔；所有入口的 UNKNOWN 按用户＋单词＋业务日期最多应用一次惩罚。任务组装仍可能同时展示同词 REVIEW 与 EXTRA，重复练习和界面负担尚未消除。以下数值示例仅说明旧行为。

**新分支新增入口导致的确定可达路径，未运行数据库复现。** S13 独立查询到期词与未解决错词，没有去重；数据库允许同词不同 `item_type`，两种任务项都会走 S2 的普通调度路径。

示例：某词既到期又在未解决错词表，入组前 `repetition=1`、EF=2.18。

| 当天行为 | 调度后连续次数 | 调度后间隔 |
| --- | --- | --- |
| 完成 `REVIEW`，答对 | 2 | 3 天 |
| 稍后完成同词的 `EXTRA`，再次答对 | 3 | 7 天，并标记 `MASTERED` |

第二次成功没有经历新的跨日间隔，却让同一词从 3 天继续推进到 7 天。另一个路径是 `REVIEW` 首次失败、重练补对后，在 `EXTRA` 再次首次失败，会再次扣 EF，因为失败去重按 itemId 隔离。

未到期但仍未解决的错词也能被加入 `EXTRA`，成功后直接重排下次日期。甚至仅有错词的一组 `DAILY` 会影响调度，而从独立 `WRONG_WORD_PRACTICE` 入口练同一批词不影响；这种差异需要明确产品理由。

建议：组装任务时按 wordId 排除重复词，并单独定义普通 `EXTRA` 是否只作为练习事件。若仍允许额外练习影响调度，必须明确提前复习和同会话多次成功的合并规则；同任务项 CAS 不能替代这些规则。

### P2-1：EF 永久下降，缺乏恢复通道（已修复）

2026-09-19：旧 q=2/4 公式不再决定 EF。每天首次真实 UNKNOWN 扣 0.20；只有通过服务端资格检查的跨日正式 KNOWN 才增加 0.05；EF 限制为 1.30～2.70。以下数学结果为旧算法基线。

**确定的数学结果。** q=4 的 EF 增量为零，四次有效失败就能到 1.30；成功不会使其恢复。

影响：早期不熟、误点或额外完形填空失败会长期影响后续增长。表中的 783 天与 16 天展示了相同连续成功次数下路径差异，但不能仅凭差异证明某个间隔最优。降到下限也不表示间隔永远是 1 天，它仍会增长，只是增长较慢。

建议：在两档交互下独立设计有界的恢复规则，例如仅在跨日首次回忆连续成功后小幅恢复，设置上下限；具体幅度通过数据验证。不要简单把所有“认识”改成 q=5：这会让每次成功都增加 EF，而答案预览、重练成功和间隔上限问题仍然存在。

### P2-2：日内重练与跨日正式复习共用计数及去重边界（已修复）

2026-09-19：请求新增 `attemptId` 和 `attemptType`。网络重试按 attemptId 幂等；每日算法效果按用户＋单词＋上海自然日记录；日内补练成功不改变 EF、正式 repetition 或间隔。跨日恢复的补练轮次仍按补练处理，不会把看过释义后的成功升级为正式复习。以下影响描述为旧行为。

**确定行为。** 普通重练最终成功计入 `repetition`；失败去重只看任务项已有 `UNKNOWN`，没有日期或会话窗口。

影响一：当日补对成为连续成功的第一步，影响后续毕业和掌握标签。

影响二：昨天第一次失败后退出，今天回来仍失败，后端仍然直接返回昨天状态，不更新 EF、失败计数或最近学习时间；今天最终补对又被算作成功。失败被过滤的范围超过了“同一天的重复尝试”。

建议：分别记录首次回忆结果和补练结果，引入学习／重学阶段与明确会话标识。补练只推进学习阶段；跨日回来应重新取得一次首次回忆信号。幂等去重与“同一会话不重复惩罚”应分别实现。

### P2-3：普通完形填空形成只惩罚、不恢复的额外通道（部分修复）

2026-09-19：同日重复惩罚已修复，完形与卡片共享每日一次 UNKNOWN 额度，每次真实失败仍单独记录。产品仍保留“完形失败可以影响调度、成功不恢复 EF”的规则，因此题目质量、词形或提示使用造成的错误仍会成为长期调度信号；提示等级尚未随作答上传。以下重复扣减描述为旧行为。

**确定行为，且为 S11 明确保留的产品决策。** 答错重置连续次数并扣 EF，答对只记事件；重新生成的新题还可继续扣减。

影响：同一词刚在卡片中失败，随后在普通完形填空再次错，会在同日被扣两次；刷更多额外题的用户也会暴露更多扣分机会。语境理解、词形或题目质量导致的失败可能被全部解释为单词不认识。新分支生成任务复用减少的是重复生成，并没有增加跨新题的同词调度去重。

建议：优先把完形填空作为独立弱项信号；如继续直接影响调度，至少限制同词同会话／同日重复降级，并区分首次自动练习与手动重新生成。保留当前规则并非编程错误，但需要记录和观察其对复习负担的影响。

### P2-4：掌握与困难标签过于粗糙（未修复）

2026-09-19：正式成功与补练已分离，减少了日内刷高 repetition 的路径，但 MASTERED 仍以 repetition 阈值判断，DIFFICULT 仍以累计 wrongCount 判断；近期失败窗口、最低保持时长及错词解决口径均未调整。

**确定行为，属于状态语义问题。** 三次连续成功即 `MASTERED`，不要求跨日、不检查已保持时长或最低间隔；`wrongCount` 是累计值，累计第三次失败即 `DIFFICULT`，下一次成功又直接变为 `REVIEWING`。

影响：容易较早标为掌握；长期偶发失误和近期持续困难没有区分。普通卡片重练成功也不会自动解决普通新词／复习词产生的错词记录，因而“错词”“困难”“已掌握”可能同时呈现不同口径。这些集合本来可以不同，但应清晰定义。

建议：用跨日首次回忆成功次数和最低保持时长定义掌握；用近期失败情况定义困难。将困难标签与学习阶段分开，明确错词解决规则。`MASTERED` 当前仍会正常到期复习，这一点是合理的。

### P2-5：旧任务、必做完形填空及新词顺序会延迟到期复习（未修复）

2026-09-19：任务选择和前端 `NEW → REVIEW → EXTRA` 顺序未在本轮修改，该问题仍存在。

**确定流程，负面影响依用户使用方式而定。** S3 优先续旧任务、优先完成当日关联完形填空；已开始的旧任务不补今天的到期词。前端还先展示新词组。

例子：昨天任务只做了一部分，今天新增很多到期词，入口仍继续昨天的任务；若一直不能完成其中难词，新到期词的入组会延后。当天完形填空因 AI 配置、额度或生成失败尚未完成时，下一组到期复习也可能受到该衔接限制。

建议：允许独立开始到期复习；将 AI 练习作为可恢复的后续活动；积压较大时优先旧词并减少新词。需要保留每组限制，但不能让每组配额被误认为积压管理策略。

### P2-6：时间模型简单，用户时区未参与调度（部分修复）

2026-09-19：复习、任务和统计涉及的业务日期已显式统一为 `Asia/Shanghai`，不再依赖 JVM 默认时区。用户设置中的 timezone 仍未参与调度；一天仍指自然日，实际经过时长及逾期程度仍不参与间隔计算。

**确定实现，跨时区影响需按部署验证。** `LocalDate.now()` 使用 JVM 默认时区；数据库有用户 `timezone`，但调度及到期筛选未读取它。Jackson 的 `time-zone` 配置不是这里显式选择用户时区的机制。

“1 天”是下一个日历日，并非至少 24 小时；23:59 成功后，次日很快就可能到期。按自然日调度本身可以接受，但应明确产品口径。

此外，无论用户准时还是逾期数周成功，算法都从原间隔按同一公式增长，再从今天起算。它不会把实际间隔用于重新判断记忆状态。

建议：统一可注入的 `Clock` 与明确时区策略；记录实际间隔。是否调整逾期成功间隔应通过数据验证，不能简单按逾期时长同比拉长。

### P3-1：没有最大间隔与数值边界保护（已修复）

2026-09-19：间隔先用 BigDecimal 和 HALF_UP 取整，再限制到 1～365，最后使用 `intValueExact()` 转换。以下 783 天和溢出风险描述为旧算法基线。

**确定缺少上限；溢出是极端风险。** EF=2.50 时第八次成功已经安排 783 天，此后继续指数增长。是否过长取决于产品目标与实际保持率，目前没有验证依据。

`BigDecimal.intValue()` 也不是溢出检查转换，极大值可能截断；普通按期使用下不是近期最可能出现的问题。更现实的需求是为产品设定可配置最大间隔，避免无依据地安排到很久以后，并用检查型转换处理异常状态。
