# 功能设计讨论

## AI 评阅格式

### 结论

当前采用“混合方案”：

- AI 负责产出结构化内容。
- 后端负责把结构化内容整理成稳定的章节骨架。
- 前端负责 Markdown 渲染和视觉排版。

### 取舍

#### 直接让 AI 输出最终 Markdown

优点：

- 改动少。
- AI 的语气和强调感更自然。

缺点：

- 格式稳定性差，标题层级、列表样式容易漂。
- 后续做统计、二次展示、移动端适配时不方便。
- 前端仍然要做视觉渲染，不能真正省掉排版成本。

#### 继续用结构化 JSON + 后端组装

优点：

- 结构稳定，便于缓存、回放和扩展。
- 章节层级统一，前端渲染更容易控制。
- 后续如需改展示风格，不必重做 AI 提示词。

缺点：

- 后端要维护一层 formatter。
- 前端仍需做一些 Markdown 样式调整。

### 当前采用的做法

- AI 返回 JSON。
- 后端把 JSON 组装成 Markdown 展示文本。
- 前端只做 Markdown 渲染和样式控制。
- 在 prompt 中只额外约束 AI：
  - 关键结论可以用 `**加粗**`
  - 英文词可以用 `` `resume` `` 这类反引号包裹
  - 如果既是关键结论又是英文词，可以用 **`resume`**这种嵌套强调

### 不纳入 prompt 的项

- 不要求 AI 自己输出固定大标题结构。
- 不额外要求 AI 把每条建议压短。

这些留给后端结构和前端样式继续控制，避免模型输出漂移。

## 完形填空与 SM2

### 当前产品决策

当前先保留现有规则：普通完形填空提交后，答错的挖空词会以 `UNKNOWN` 参与 SM2 更新；用户重新生成的普通完形填空也继续按同样规则影响 SM2。

保留原因：

- 单词卡片的学习、回忆、重练反馈仍然偏少。
- 完形填空能补充语境应用层面的反馈。
- 对个人学习体验而言，答错语境应用题后让词更快回到复习队列，目前看起来更合理。

### 备选建议规则

后续如果发现用户反复刷完形填空导致复习节奏被放大，可以考虑切换为更严格的边界：

- SM2 只由单词卡片的学习、回忆、重练反馈驱动。
- 完形填空只记录练习结果、错题、AI 评阅和应用能力统计。
- 自动生成的第一篇完形填空最多作为轻量弱项信号，不直接重复降级 SM2。
- 用户手动重新生成的完形填空视为额外练习，不影响 SM2。
- 错词专项完形填空继续不影响 SM2。

这个备选方案的优点是学习调度边界更干净，缺点是完形填空对复习间隔的直接反馈会变弱。

或

- **单词学习/回忆阶段**：影响 SM2，作为主记忆调度依据。
- **学习完成后自动生成的第一篇完形填空**：可以影响弱项记录、错词、统计；是否影响 SM2 要谨慎。（项目目前会影响和参与 SM2）
- **用户手动重新生成的完形填空**：不影响 SM2，只记录练习结果、AI 评阅、错题分析。
- **错词专项完形填空**：继续不影响 SM2。

## 完形填空缓存与重新生成

### 当前产品决策

普通首次生成完形填空时，可以复用缓存；用户点击“重新生成练习”时，必须跳过缓存，重新调用 AI 生成一篇新的完形填空。

### 缓存边界

完形填空缓存不允许跨用户复用。

当前缓存来源哈希包含：

- `userId`
- `dailyTaskId`
- `wordbookId`
- `sourceType`
- 目标词 ID 列表
- 挖空词 ID 列表

缓存查询时也会按 `userId` 过滤，因此普通首次生成只可能复用“同一个用户、同一个任务上下文、同一组词”之前生成过的缓存，不会使用其他用户生成的完形填空。

### 重新生成规则

- 普通“生成练习”：允许命中当前用户自己的缓存。
- 已有题目后点击“重新生成练习”：前端传 `regenerate=true`。
- 后端收到 `regenerate=true` 后跳过缓存命中逻辑，直接进入新的 AI 生成流程。

## 重练阶段与 SM2

**1. 普通学习里的重练阶段（新词 retry/复习词 retry）**

- 第一次回忆阶段点“不认识”：会影响 SM2，提交 `UNKNOWN`。
- 进入重练后，如果这个词再次点“不认识”：**不会再次影响 SM2**。
  - 代码里有去重判断：如果 item 已经是 `UNKNOWN`，再次提交 `UNKNOWN` 会直接返回，不再调用 `spacedRepetitionService.applyFeedback()`。
- 重练里最终点“认识”：**会影响 SM2**，提交 `KNOWN`。

所以普通重练阶段里，**重复答错不会重复影响 SM2**，但最后答对会再按 `KNOWN` 更新一次。

**2. 错词专项重练任务**

这个完全不影响 SM2。

`WRONG_WORD_PRACTICE` 会走 `submitWrongWordPracticeFeedback()`，这里只记事件、错词 resolved/unresolved、任务进度，不调用 `spacedRepetitionService.applyFeedback()`。

所以一句话：

> 普通重练里“再次答错”不会重复影响 SM2；错词专项重练完全不影响 SM2；普通重练最后点“认识”会影响 SM2。

## AI 提示词解析缓存

### 当前产品决策

AI 提示词管理当前先使用后端单机内存缓存，不引入 Caffeine、Guava 或 Redis。

当前实现是：

- 使用 `ConcurrentHashMap<AiPromptFeatureType, ResolvedAiPromptTemplate>` 缓存解析后的提示词。
- 缓存 key 只有当前 3 个 AI 功能：
  - `WORD_QA`
  - `CLOZE_QUIZ`
  - `CLOZE_REVIEW`
- AI 调用前 `resolve(featureType)` 先查内存缓存。
- 缓存未命中时再查询功能绑定和模板表。
- 管理端创建、编辑、复制、切换当前模板、恢复默认、停用当前模板时，主动清理对应功能缓存。

### 为什么暂不引入第三方缓存库

当前场景非常小：

- 缓存键固定且只有 3 个。
- 缓存值很小，只是一套已解析提示词。
- 没有容量淘汰需求。
- 没有复杂 TTL、统计命中率或分布式一致性需求。
- 提示词改动频率低，AI 调用读取频率高。
- 写操作已经可以主动失效缓存。

在这个规模下，引入 Caffeine/Guava 会增加依赖和配置复杂度，但收益有限。`ConcurrentHashMap` 足够直接、可控，也容易测试。

### 风险边界

当前实现适合单机部署和固定少量 AI 功能，不把它设计成通用缓存框架。

需要注意：

- 多实例部署时，某个实例上的管理端写操作只能清理本实例内存缓存。
- 如果另一个实例没有收到失效通知，可能短时间继续使用旧提示词。
- 后端代码里的内置默认提示词如果被修改，仍然需要重新构建和重启后端。

### 后续升级方向

如果后续出现以下情况，再升级缓存方案：

- AI 功能类型明显增多。
- 后台需要手动刷新缓存、查看命中率或缓存状态。
- 多实例部署后要求提示词切换跨实例立即生效。
- 需要 TTL、最大容量、淘汰策略、刷新策略等通用缓存能力。

推荐演进顺序：

1. 单机阶段：继续使用 `ConcurrentHashMap`。
2. 单机但功能变多：改为 Caffeine，获得 TTL、容量限制和统计能力。
3. 多实例阶段：使用 Redis 发布订阅做缓存失效通知，保留本地一级缓存；或按实际压力改为 Redis 缓存。

当前结论：先保持轻量本地缓存，后续 Redis 需求明确后再做分布式失效。

## AI 输出流式体验

### 当前状态

当前 3 个 AI 功能都不是“模型 token 真流式到前端”：

- **AI 问答**：前端等待后端完整 JSON 响应。
- **AI 完形填空**：前端显示生成中动画，后端等待 AI 返回完整 JSON 后再校验、挖空、入库。
- **AI 评阅**：前端使用 SSE 打字机效果，但后端是先完整生成评阅 JSON，再整理成展示文本并分段推送，属于假流式。

后端底层 AI 客户端虽然有 `stream=true` 配置，但当前实现仍然会一次性读取完整响应后再解析，因此还没有做到模型边输出、前端边展示。

### 当前产品决策

短期内：

- AI 完形填空维持现状。
- AI 评阅维持现有假流式，不改真流式。
- 暂不为完形填空做内容级假流式展示。

### 取舍

#### AI 完形填空

不推荐内容级假流式。

原因：

- 完形填空需要完整短文和完整 JSON。
- 后端还要做挖空、校验、候选词生成、答案解析和入库。
- 在校验完成前，前端不适合展示半成品题目。
- 内容级假流式只能改善等待感，不能减少真实生成耗时，且容易让用户看到不可用的中间内容。

更合适的优化方向是阶段式等待体验：

- 生成中
- 正在整理短文
- 正在挖空和校验
- 正在生成答案解析

但这属于加载体验优化，不是输出流式化。当前先不改。

#### AI 评阅

当前假流式可以继续保留。

原因：

- 评阅现在仍要求 AI 输出结构化 JSON，便于缓存、回放和前端稳定展示。
- 真流式 JSON 不方便边解析边展示，容易遇到半截 JSON、格式漂移和恢复问题。
- 如果改成真流式 Markdown，体验会更快，但会牺牲结构稳定性和后续统计扩展能力。

当前结论：AI 评阅继续使用“后端完整生成 + SSE 打字机展示”的假流式方案。

### 后续可能的优化方向

如果后续要优先提升体感速度，建议先从 **AI 问答** 做真流式：

- AI 问答不需要复杂入库校验。
- 用户提问后能更快看到首字输出。
- 改造风险低于完形填空和 AI 评阅。

完形填空和 AI 评阅暂不进入真流式改造队列。

## AI 问答真流式方案

### 当前产品决策

AI 问答优先改成真流式，采用 **SSE/HTTP 流**，不使用 WebSocket，也不让前端直接请求 AI 服务商。

推荐链路：

```text
前端 -> 后端 AI 问答流式接口 -> AI 服务商流式接口
                         -> 后端边接收 token 边转发给前端
                         -> 后端同时累积完整内容
                         -> 流结束后统一解析、缓存、记录日志
```

### 为什么用 SSE，不用 WebSocket

AI 问答是典型的“服务端持续向前端推文本”场景，前端不需要高频双向实时通信。

SSE 更合适：

- 基于 HTTP，实现和调试简单。
- 天然适合服务端单向推送文本。
- 前端可以用 `fetch + ReadableStream` 或 `EventSource` 读取。
- 对当前项目的登录、网关、部署方式侵入更小。

WebSocket 更适合聊天室、协同编辑、实时游戏这类双向频繁通信。AI 问答使用 WebSocket 偏重，暂不采用。

### 为什么不让前端直连 AI

不推荐“前端直接请求 AI 服务商，流式结束后再写回后端”。

原因：

- API Key 会暴露到浏览器，风险很高。
- 会绕过后端的模型配置、提示词管理、限额、日志、缓存和审计。
- 用户可以篡改 prompt、模型参数或响应内容后再写回后端。
- 后端无法保证写入内容可信。
- 后续做计费、频控、内容安全、黑名单会更困难。

所以前端只负责展示，后端负责：

- API Key
- 当前启用的提示词模板
- 用户权限和限额
- 缓存命中和写入
- AI 调用日志
- 最终入库内容可信度

### 入库策略

真流式不代表每个 token 都入库。

当前设计：

- AI 每输出一段 token，后端立即转发给前端。
- 后端同时把 token append 到内存缓冲。
- 收到结束事件后，后端拿到完整内容。
- 后端解析完整 JSON，写入缓存表和 AI 调用日志。
- 如果命中缓存，后端也可以把缓存内容拆成 chunk 推给前端，保持同样的流式体验。

边界处理：

- AI 中途失败：记录失败日志，前端显示失败状态，不保存半截答案。
- JSON 半截不可解析：等待流结束后再解析，不在前端依赖半截 JSON。
- 用户关闭页面：首版不额外保证断开后继续落库，后续如需要可增加异步任务托底。

## 多设备登录

### 当前状态

当前认证采用无状态 JWT：

- 登录时签发 `accessToken`，同时把 `refresh_token` 写入 HttpOnly Cookie。
- 后端不保存登录会话表，也不记录当前有效 refresh token。
- 新设备登录不会让旧设备 token 失效。
- 退出登录只清除当前浏览器的 `refresh_token` Cookie，不会踢掉其他设备。

因此当前实际行为是：**允许同一用户多设备同时登录，不限制设备数量，也没有单点登录或踢下线机制**。

### MVP 阶段决策

MVP 阶段暂不增加多设备限制。

原因：

- 背单词核心流程暂时不依赖单设备登录。
- 多设备并存对当前学习体验影响较小。
- 暂不引入会话表、设备管理、刷新令牌失效、踢下线等额外复杂度。
- 可以把研发精力优先放在学习流程、AI 能力和管理端基础能力上。

### 后续可选方案

如果后续出现账号共享限制、安全退出全部设备、设备管理等明确需求，再考虑增加会话管理：

- **允许多设备但可管理**：新增登录设备/会话表，用户或管理员可以单独踢下线某台设备。
- **只允许单设备**：新登录时更新用户 `tokenVersion` 或清空旧 session，让旧 token 失效。
- **按设备类型限制**：例如 Web 端只保留一个登录，移动端单独保留一个登录。

当前结论：MVP 先保持多设备并存，后续需求明确后再做会话管理。

### 修改密码踢出所有设备

修改密码属于高安全动作，后续实现时应让该用户所有旧设备的登录态失效。

推荐方案：使用用户级 `token_version`。

实现思路：

1. `user` 表增加 `token_version` 字段，默认 `0`。
2. 签发 access token 和 refresh token 时，把当前 `token_version` 写入 JWT claims。
3. 每次解析 JWT 后，除了校验签名和过期时间，还读取用户当前 `token_version`。
4. 如果 JWT 中的版本和数据库当前版本不一致，直接拒绝请求。
5. 修改密码成功后，将用户 `token_version + 1`。

这样修改密码后，旧设备上的 access token 和 refresh token 都会失效；当前设备也需要重新登录。

备选方案：使用 `password_changed_at`，JWT 校验时比较 `iat` 是否早于密码修改时间。但该方案依赖时间精度和时区处理，后续扩展“退出全部设备”“管理员强制下线”也不如 `token_version` 直接。

当前结论：MVP 暂不实现；后续做修改密码功能时，优先采用 `token_version` 方案。

## AI 公共额度查询优化

### 当前状态

公共 AI 调用限额仍然通过 `ai_call_log` 统计当天使用次数：

- 按 `user_id` 过滤。
- 只统计 `config_scope = PUBLIC`。
- 只统计当天 `created_at` 范围内的记录。

### 当前取舍

短期先保留日志表计数，不改成独立计数表。

原因：

- AI 调用本身远慢于一次索引范围计数。
- 当前 `ai_call_log` 已有 `user_id + created_at` 索引。
- 本次补充 `user_id + config_scope + created_at` 复合索引后，额度查询更贴合现有条件。
- 日志表计数逻辑简单、可审计，便于在管理端排查用户调用记录。

### 后续优化方向

1. 先依赖复合索引，保持当前实现。
2. 如果后续日志量和并发明显上来，再考虑拆每日额度统计表，例如 `ai_quota_usage`。
3. 再往后才考虑 Redis 计数 + 数据库兜底。

当前结论：**先补索引，不改计数模型**。

## 公共 AI 配置缓存策略

### 当前状态

公共 AI 配置当前不做本地缓存。每次 AI 调用前，`AiConfigResolver` 都会读取当前激活且启用的公共配置，并使用其中的模型、Base URL、温度、流式开关和 `dailyQuotaPerUser`。

### 当前取舍

短期先保持每次查表。

原因：

- AI 调用本身远慢于一次配置查询。
- 管理员修改公共 AI 配置后可以立即生效，不需要额外缓存失效逻辑。
- 当前项目仍以单机本地开发和 MVP 验证为主，过早引入 Redis 会增加部署复杂度。

### 后续优化方向

1. 单机阶段：先加本地内存缓存，缓存当前 active 公共配置；管理员新增、编辑、启用、禁用、激活配置时清缓存。
2. 多实例阶段：使用 Redis 缓存公共配置，或使用 Redis Pub/Sub 通知各实例清本地缓存。
3. 折中方案：本地缓存加短 TTL，例如 30 秒，允许配置变更有短暂延迟。

### 和额度计数的区别

公共 AI 配置缓存只解决“读取当前配置”的开销；每日额度统计仍是另一条线。

后续如果并发上来，额度统计可以独立演进为：

- `ai_quota_usage` 每日额度表；
- 或 Redis 计数 + 数据库日志审计。

当前结论：**公共配置暂不缓存；后期先本地缓存，多实例再 Redis**。
