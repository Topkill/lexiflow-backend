# 功能设计讨论

## AI 评阅格式

### 结论

当前采用“混合方案”：

- AI 负责产出结构化内容。
- 后端负责把结构化内容整理成稳定的章节骨架。
- 前端负责 Markdown 渲染和视觉排版。

### 取舍

#### 直接让 AI 输出最终 Markdown

优点：

- 改动少。
- AI 的语气和强调感更自然。

缺点：

- 格式稳定性差，标题层级、列表样式容易漂。
- 后续做统计、二次展示、移动端适配时不方便。
- 前端仍然要做视觉渲染，不能真正省掉排版成本。

#### 继续用结构化 JSON + 后端组装

优点：

- 结构稳定，便于缓存、回放和扩展。
- 章节层级统一，前端渲染更容易控制。
- 后续如需改展示风格，不必重做 AI 提示词。

缺点：

- 后端要维护一层 formatter。
- 前端仍需做一些 Markdown 样式调整。

### 当前采用的做法

- AI 返回 JSON。
- 后端把 JSON 组装成 Markdown 展示文本。
- 前端只做 Markdown 渲染和样式控制。
- 在 prompt 中只额外约束 AI：
  - 关键结论可以用 `**加粗**`
  - 英文词可以用 `` `resume` `` 这类反引号包裹
  - 如果既是关键结论又是英文词，可以用 **`resume`**这种嵌套强调

### 不纳入 prompt 的项

- 不要求 AI 自己输出固定大标题结构。
- 不额外要求 AI 把每条建议压短。

这些留给后端结构和前端样式继续控制，避免模型输出漂移。

## 完形填空与 SM2

### 当前产品决策

当前先保留现有规则：普通完形填空提交后，答错的挖空词会以 `UNKNOWN` 参与 SM2 更新；用户重新生成的普通完形填空也继续按同样规则影响 SM2。

保留原因：

- 单词卡片的学习、回忆、重练反馈仍然偏少。
- 完形填空能补充语境应用层面的反馈。
- 对个人学习体验而言，答错语境应用题后让词更快回到复习队列，目前看起来更合理。

### 备选建议规则

后续如果发现用户反复刷完形填空导致复习节奏被放大，可以考虑切换为更严格的边界：

- SM2 只由单词卡片的学习、回忆、重练反馈驱动。
- 完形填空只记录练习结果、错题、AI 评阅和应用能力统计。
- 自动生成的第一篇完形填空最多作为轻量弱项信号，不直接重复降级 SM2。
- 用户手动重新生成的完形填空视为额外练习，不影响 SM2。
- 错词专项完形填空继续不影响 SM2。

这个备选方案的优点是学习调度边界更干净，缺点是完形填空对复习间隔的直接反馈会变弱。

或

- **单词学习/回忆阶段**：影响 SM2，作为主记忆调度依据。
- **学习完成后自动生成的第一篇完形填空**：可以影响弱项记录、错词、统计；是否影响 SM2 要谨慎。（项目目前会影响和参与 SM2）
- **用户手动重新生成的完形填空**：不影响 SM2，只记录练习结果、AI 评阅、错题分析。
- **错词专项完形填空**：继续不影响 SM2。

## 完形填空缓存与重新生成

### 当前产品决策

普通首次生成完形填空时，可以复用缓存；用户点击“重新生成练习”时，必须跳过缓存，重新调用 AI 生成一篇新的完形填空。

### 缓存边界

完形填空缓存不允许跨用户复用。

当前缓存来源哈希包含：

- `userId`
- `dailyTaskId`
- `wordbookId`
- `sourceType`
- 目标词 ID 列表
- 挖空词 ID 列表

缓存查询时也会按 `userId` 过滤，因此普通首次生成只可能复用“同一个用户、同一个任务上下文、同一组词”之前生成过的缓存，不会使用其他用户生成的完形填空。

### 重新生成规则

- 普通“生成练习”：允许命中当前用户自己的缓存。
- 已有题目后点击“重新生成练习”：前端传 `regenerate=true`。
- 后端收到 `regenerate=true` 后跳过缓存命中逻辑，直接进入新的 AI 生成流程。

## 重练阶段与 SM2

**1. 普通学习里的重练阶段（新词 retry/复习词 retry）**

- 第一次回忆阶段点“不认识”：会影响 SM2，提交 `UNKNOWN`。
- 进入重练后，如果这个词再次点“不认识”：**不会再次影响 SM2**。
  - 代码里有去重判断：如果 item 已经是 `UNKNOWN`，再次提交 `UNKNOWN` 会直接返回，不再调用 `spacedRepetitionService.applyFeedback()`。
- 重练里最终点“认识”：**会影响 SM2**，提交 `KNOWN`。

所以普通重练阶段里，**重复答错不会重复影响 SM2**，但最后答对会再按 `KNOWN` 更新一次。

**2. 错词专项重练任务**

这个完全不影响 SM2。

`WRONG_WORD_PRACTICE` 会走 `submitWrongWordPracticeFeedback()`，这里只记事件、错词 resolved/unresolved、任务进度，不调用 `spacedRepetitionService.applyFeedback()`。

所以一句话：

> 普通重练里“再次答错”不会重复影响 SM2；错词专项重练完全不影响 SM2；普通重练最后点“认识”会影响 SM2。

## AI 提示词解析缓存

### 当前产品决策

AI 提示词管理当前先使用后端单机内存缓存，不引入 Caffeine、Guava 或 Redis。

当前实现是：

- 使用 `ConcurrentHashMap<AiPromptFeatureType, ResolvedAiPromptTemplate>` 缓存解析后的提示词。
- 缓存 key 只有当前 3 个 AI 功能：
  - `WORD_QA`
  - `CLOZE_QUIZ`
  - `CLOZE_REVIEW`
- AI 调用前 `resolve(featureType)` 先查内存缓存。
- 缓存未命中时再查询功能绑定和模板表。
- 管理端创建、编辑、复制、切换当前模板、恢复默认、停用当前模板时，主动清理对应功能缓存。

### 为什么暂不引入第三方缓存库

当前场景非常小：

- 缓存键固定且只有 3 个。
- 缓存值很小，只是一套已解析提示词。
- 没有容量淘汰需求。
- 没有复杂 TTL、统计命中率或分布式一致性需求。
- 提示词改动频率低，AI 调用读取频率高。
- 写操作已经可以主动失效缓存。

在这个规模下，引入 Caffeine/Guava 会增加依赖和配置复杂度，但收益有限。`ConcurrentHashMap` 足够直接、可控，也容易测试。

### 风险边界

当前实现适合单机部署和固定少量 AI 功能，不把它设计成通用缓存框架。

需要注意：

- 多实例部署时，某个实例上的管理端写操作只能清理本实例内存缓存。
- 如果另一个实例没有收到失效通知，可能短时间继续使用旧提示词。
- 后端代码里的内置默认提示词如果被修改，仍然需要重新构建和重启后端。

### 后续升级方向

如果后续出现以下情况，再升级缓存方案：

- AI 功能类型明显增多。
- 后台需要手动刷新缓存、查看命中率或缓存状态。
- 多实例部署后要求提示词切换跨实例立即生效。
- 需要 TTL、最大容量、淘汰策略、刷新策略等通用缓存能力。

推荐演进顺序：

1. 单机阶段：继续使用 `ConcurrentHashMap`。
2. 单机但功能变多：改为 Caffeine，获得 TTL、容量限制和统计能力。
3. 多实例阶段：使用 Redis 发布订阅做缓存失效通知，保留本地一级缓存；或按实际压力改为 Redis 缓存。

当前结论：先保持轻量本地缓存，后续 Redis 需求明确后再做分布式失效。
